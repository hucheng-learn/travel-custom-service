旅游客服系统测试用例

适用于研发联调、自测和验收。覆盖六类商品咨询、订单与行程、知识问答、多轮对话、退款、工单、会话接口及异常恢复。

1. 测试准备

  • 启动旅游中台和客服服务，确认客服库已完成迁移。打开 客服调试页 或 Swagger。业务时区使用 Asia/Shanghai。
  • 除步骤明确要求复用会话外，每条用例新建会话。连续话术按箭头顺序逐句发送。页面订单卡片用 orderId，文本用 orderNo。用 Swagger 时请求头填 X-User-Id，每个新输入使用一个新的 UUID 作为 messageId，重试原消息沿用原 ID 和完整请求体。
  • 默认关闭真实退款开关。需要验证入库的退款用例在隔离测试中台开启 REFUND_WRITE_ENABLED=true。每条写入或故障用例使用独立的可退款明细，或恢复该测试环境的种子快照后再跑。没有合适数据或故障注入环境时，记录为阻塞。
  • 验收时按当前中台数据核对金额、库存和状态。商品基线使用指定日期；如果日期已过去且中台过滤历史供给，换为同路线、同商品有供给的日期并记录当前基线。故障恢复后复测原操作。

6. 多轮对话与会话状态

编号场景操作预期结果
D01用 A 发「帮我查订单」，记下订单任务 taskId。发「帮我查行程」，记下行程任务 ID 和会话 ID。重启客服服务后加载原会话，发订单卡片 73；行程返回后再单独发同一张卡片。重启后历史保留前两轮，当前任务和暂停任务 ID 与重启前一致。第一张卡完成行程，原订单任务按原 ID 恢复并追问订单号。第二张卡完成订单和支付查询，最终历史四轮，活动任务和暂停列表均为空。
D02用 A 发「申请退款」→ A 订单号 →「部分退款」→「50」。被追问退款原因时记下 taskId；发「帮我查行程」并发卡片 73。行程完成后恢复同一退款任务，继续询问原因。补「行程调整」后，确认摘要仍为 A、明细 73、50.00。点击「不提交」后无退款写入。
D03发「2026-11-20 北京有哪些酒店」→「暂停所有任务」→「继续上一个任务」→「取消当前任务」。暂停时保留已填的地区和入住日期；继续时恢复同一个任务，并再次追问退房日期；取消后任务状态清理。
D04用 A 发「帮我查订单」→「退款审核通过就到账了吗」→ A 订单号。知识问答有来源；原订单任务保持等待，最后收到订单号可直接完成。
D05用 A 走到部分退款确认摘要。发「修改订单」并补发其他订单；若用 B 订单号，保持用户 73。提示重新核对订单或拒绝他人订单。旧目标、金额和确认卡不可继续用于提交；已收集内容的取舍应在交互中明确。
D06用用户 73 建两个会话，只在其中一个发「帮我查订单」。再用用户 199 查看用户 73 的会话状态和历史。两个会话各自保存状态；用户 199 查询他人会话时返回 HTTP 404。
D07在同一新会话完成三轮简单对话。调用历史接口，先传 pageSize=2，再用响应的 nextBeforeSeq 作为下一页的 beforeSeq。首次返回最新两轮，页内按时间正序展示；下一页返回更早一轮，两页无重复、无漏项。

7. 退款

R05 和 R08 需要开启真实退款。只验证预检时，核对摘要后点「不提交」。

编号场景操作预期结果
R01用 B 发「申请退款」→ B 订单号 →「全额」→「行程有变」；核对确认摘要后点「不提交」。单明细自动选中 199。摘要中有订单、明细、原因和 3469.20；拒绝确认后无新申请。
R02用 B 发「申请退款」→ B 订单号 →「部分退款」。分别试输 0、-1、1.001；接着填 3469.21 和原因。重新按提示填 50.00。非正金额、超过两位小数和超额金额均被拒绝。50.00 可生成正确摘要，之前的失败均无写入。
R03准备一笔本人订单，至少两条可退款明细，另备一个不属于该单的明细 ID。申请退款时先发错误明细 ID，再选一条本单有效明细继续。系统列出可选明细；错误明细被拒绝。继续预检时，商品、金额上限和确认摘要都对应所选明细。
R04用 B 生成 80.00 的确认卡，记录确认 ID；发「修改金额 50」，再点旧卡和新卡的「确认提交」。本例保持写开关关闭。新摘要金额为 50.00、确认 ID 更新；旧卡失效。新卡提示真实提交未启用，中台无新增申请。
R05隔离环境用 B 提交部分退款 50.00。第一次确认后，先用原 messageId 重试，再用新 messageId 发送同一确认卡及同一决定。用回执编号查进度并核对中台。第一次返回真实申请编号和中台状态，初始通常为待处理。原消息重试回放同一轮次，同确认 ID 复用原申请回执。中台仅新增 1 笔，订单、明细、金额一致。
R06用户 4 发「查退款进度 RFDQ0000000004」，再用用户 73 发同样的消息。用户 4 看到申请编号、退款完成状态、565.61 及关联成功退款流水。用户 73 无法读取该申请详情。

9. 接口、SSE 与异常恢复

SSE 事件和断流用调试页或浏览器网络面板查看。需要控制上游响应、并发或数据库连接的场景在隔离联调环境执行。

编号场景操作预期结果
I01用户 73 分别新建两个会话，分别关闭和开启 SSE，发送「帮我查订单」后发卡片 73。JSON 一次给完整回复；SSE 收到 accepted、文本 delta 和唯一 done。拼接文字与 done 一致，卡片和最终任务状态与 JSON 业务结果一致。
I02流式发送「帮我查订单」。收到 accepted 至 done 之间断开连接，必要时用测试环境延时保证时机。用原消息重试；轮次落库后重启客服，加载原会话并补卡片。处理中可提示稍后重试；完成后回放同一 turnId。重启后仍等待订单，补卡可继续，原轮次只有一条历史。
I03用 T01 的流程新建一张确认卡，通过 SSE 提交，在收到最终事件前断流，随后用原确认消息重试。最终拿到同一工单回执；仅创建一次工单及创建事件。
I04用固定 messageId 发「帮我查订单」。重发同 ID 同内容，再用相同 ID 改成「帮我查行程」。同内容回放原轮次；改内容返回 HTTP 409 和 MESSAGE_ID_CONFLICT，状态仍为订单任务。
I05分别提交空白文本、非 UUID 的 messageId 和 ID 为 0 的订单卡片。另对业务接口移除用户头。正常身份的畸形请求返回 HTTP 422；缺失身份返回 HTTP 401。错误响应带错误码和追踪号。
I06通过中台延时让请求 A 保持处理中；在同一会话发送请求 B。A 完成后再按提示重试 B。处理中返回可重试的 TURN_IN_PROGRESS；两个任务状态不相互覆盖，历史可区分两个轮次。
I07先用 A 创建会话并发「帮我查订单」。让中台订单详情超时或返回异常，再发订单卡片。恢复中台后按提示补发同一张卡作为新消息。故障时提示暂时无法查询，和 O04 的空结果有区别，仍等待补单；恢复后可完成查询。
I08建好会话并记录状态版本，令客服库在一次轮次保存时故障。恢复连接后检查状态与历史，再使用原消息 ID 按错误提示重试。客服给出可重试结果，已提交状态维持原版本，失败轮不冒充已完成。库恢复后可完成原请求，历史仅出现一条已完成记录。
I09模型服务超时时发「帮我查订单」并补 A 订单号。另开会话，让模型返回不符合结构的计划，再发同样的首轮话术。超时时按本地规则完成明确查询。计划结构无效时提示澄清，无错误业务结果；模型恢复后可处理下一轮。
I10执行 O01 一次、I07 一次和 T01 一次，记录 X-Trace-Id，在客服日志和客服库核对。能从追踪号找到对应请求、轮次、轨道、动作结果和耗时。工单创建事件可关联工单和操作者。日志不暴露原始证件号、手机号、密钥或连接串。
